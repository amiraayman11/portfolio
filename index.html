02 / BUG ARCHIVE

Case files from the field.

Not “I clicked and it broke.” These are the bugs where investigation mattered.

CASE #001 · WORKFLOW

The notification that never arrived

Reassign→DB updated→Core action→Notification ✕

Symptom ≠ root cause

What made it tricky

The user action looked successful and the underlying record changed, but the expected notification was missing. A shallow UI check could have marked the flow as passed.

How I investigated

I separated the core action from the side effect: verified the workflow, checked the stored state and narrowed the failure to notification logic rather than the reassignment itself.

QA value

The report pointed developers toward the failing layer and the fix was regression-tested across the surrounding flow.

CASE #002 · CROSS-FLOW

Fix one thing. Break the next thing.

Email link→Session expired→Acceptance blocked

The bug lived between systems.

The challenge

An acceptance journey depended on an email entry point and session/authentication behavior. The failure was not obvious when testing the page in isolation.

My approach

I tested the journey as the user actually experiences it, leaving the application, opening the email action, returning through the link and observing session state.

Lesson

End-to-end QA means testing transitions and dependencies, not just screens.

CASE #003 · CONFIGURATION

SMS disabled. OTP still invited itself.

SMS OFF→User action→OTP dialog appears

Configuration is a test dimension.

Why it mattered

The product exposed an OTP experience even though the related SMS capability was disabled, creating a contradictory and potentially blocking user journey.

How I thought about it

I treated feature configuration as part of the test matrix and checked whether downstream UI behavior respected the user's notification/2FA state.

QA value

This catches the class of bugs that only appears when valid settings combine in unexpected ways.

CASE #004 · API / DELETE

“Permanently delete” → HTTP 404

Confirm purge→404→Transaction rollback

UI promise vs. backend reality.

Evidence

The confirmation UI promised a permanent deletion, while the network request failed and the purge transaction rolled back.

Investigation mindset

Instead of reporting only “delete doesn't work,” I connected the visible failure to the HTTP behavior and transaction outcome, making the defect much more actionable.

What I would show here

In the final portfolio this case can include a sanitized screenshot, request/response snippet and a tiny “expected vs actual” timeline.

05 / MY QA LOOP

How I attack a problem.

Question the requirement

What should happen? What isn't stated? Which business rule changes the answer?

Design the paths

Happy path, negative cases, boundaries, permissions, configuration combinations and real user behavior.

Follow the evidence

UI → network → API → data → background behavior. Stop when the system tells a coherent story.

Report for action

A useful bug report reduces ambiguity: reproduce, show impact, attach evidence, isolate the failing layer.

Retest beyond the fix

Verify the fix and the nearby workflows most likely to regress.
